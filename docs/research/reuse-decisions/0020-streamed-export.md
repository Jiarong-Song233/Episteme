# 复用决策记录 0020：导出逐行写出

日期：2026-11-16。

## 要解决的问题

`pnpm workbench export` 先把整张图的记录和伴生数据读进内存，拼成一个 JSON 字符串，再整个写入文件。内存占用是文件大小的好几倍；而且 V8 的单个字符串最多约 5.4 亿个字符，图再大一点，导出会直接失败，备份做不出来。

## 实测（本机，Node 24，脚本造的图，未提交）

| 图 | 方式 | 用时 | 峰值内存（进程起点约 50 MB） |
| ---- | ---- | ---- | ---- |
| 59 MB | 原来整体拼接 | 0.6 s | 219 MB |
| 59 MB | 逐行写出 | 0.7 s | 88 MB |
| 59 MB | 导入 | 1.1 s | 308 MB |
| 574 MB | 原来整体拼接 | 5.9 s | 1,427 MB |
| 574 MB | 逐行写出 | 7.2 s | 181 MB |
| 574 MB | 导入 | 10.0 s | 1,798 MB |

这些图里的文字以中文为主。字符串上限按字符数算，一个汉字在 UTF-8 里占 3 个字节，所以 574 MB 的文件还没有碰到上限；以英文为主的内容，文件到约 512 MB 就会碰到。

## 参考

- better-sqlite3 的 `Statement.iterate()`：逐行读取，不把结果集一次性放进内存。本仓已经在用这个库。
- Node 的 `crypto.Hash` 可以分段 `update`，结果和一次性计算相同。
- 流式 JSON 解析可以用 [stream-json](https://github.com/uhop/stream-json)（BSD-3-Clause）。它是新依赖，要先批准，所以这一步没有用它。

## 决定

- 导出在同一个独占事务里过两遍：第一遍逐行算校验值，第二遍逐行写文件，每攒到约 1 MB 写一次。两遍读到的是同一张图。
- **文件格式不变**：写出的内容和原来整体序列化的结果逐字节相同，旧文件、旧版本都能照常读。测试直接验证了这一点：文件内容等于把它解析后再序列化的结果。
- 写到一半失败时删掉不完整的文件，“不覆盖已有文件”和“只有文件主人能读”（`0o600`）照旧。
- `exportGraph` 只返回文件头（来源、计数、校验值），不再把整张图带回调用方。调用方原来也只用这些字段。
- 没有新依赖，也没有改存储。

## 局限

- **导入还是整体读入。** 574 MB 的文件峰值约 1.8 GB；超过字符串上限的文件导入不了。要改成流式导入，需要流式 JSON 解析器（如 stream-json，新依赖，待批准），或者为这个格式手写解析器（不符合“优先成熟实现”的约定）。
- 导出仍是明文。
- 只在本机测过，没有在内存更小的机器上测。
