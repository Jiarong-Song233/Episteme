# 第三轮评测：与 Open WebUI 对比（2026-11-02）

这一轮第一次真正运行了成熟产品。经用户点名授权，比的是 Open WebUI 0.12.5。

**结论先说：**

- **默认配置不能代表 Open WebUI。** 它默认的英文嵌入模型读不好中文，69 次只答对 13 次。换成多语言模型、取 6 段后是 63/69，和 Episteme 的 66/69 只差 3 次。这点差距在同作者出题的小题集上不足以说谁更好。
- **两者最大的区别是不在材料范围内的问题。** 对完全无关的问题，Open WebUI 的所有配置 12 次都用常识作答，通常会注明不是来自材料；Episteme 12 次都拒答。这是默认提示词的设计差异，不一定是缺陷，要看用户想要什么。
- **它的现成能力比预想的多。** 保存理解、新会话复用、只读共享、另一个人提问时引用，这些都实际跑通了。Episteme 没有测到的优势是保留修正历史，见第 4 节。
- **小材料上，直接贴全部材料依然是答对最多的（69/69）。** 所以问答不能作为 Episteme 的卖点。

## 1. 怎么复现

```bash
uv venv --python 3.12 <目录>/venv
VIRTUAL_ENV=<目录>/venv uv pip install --only-binary :all: open-webui==0.12.5
pnpm exec tsc -b
node scripts/evaluate.mjs --repeats 3 --max-calls 300 --questions questions-round-3.json --no-journey --systems episteme,paste-all,open-webui,open-webui-zh,open-webui-zh-hybrid,open-webui-zh-k6 --openwebui-home <目录> --out result.json
node scripts/evaluate-openwebui-probe.mjs --openwebui-home <目录> --out probe.json
```

还需设置模型环境变量，并把 `EPISTEME_MODEL_MAX_CALLS` 设为 300、`EPISTEME_MODEL_MAX_TOKENS` 设为 1000000。不设的话 Episteme 客户端自带的额度会让后面的题报错，这一轮就因此作废过一次。

| 项目 | 取值 |
| --- | --- |
| 模型 | 所有系统相同：magpie 网关上的 `auto/deepseek-v4.1-flash` |
| 材料和题目 | 和第二轮相同，见 [questions-round-3.json](questions-round-3.json)，每题 3 次 |
| 原始结果 | [results/round-3.json](results/round-3.json)，[results/round-3-probe.json](results/round-3-probe.json) |
| 运行方式 | 第三方进程只运行、不并入本仓库；只监听本机，关闭遥测，数据目录用完即删 |
| 模型请求 | 经评测进程内的代理转发和计数，Open WebUI 拿不到真实 key。它自己决定发起的调用也算在内 |

前五个系统在同一次运行里跑完，`open-webui-zh-k6` 是随后单独跑的，所以它的数字可能受 `auto/` 路由变化影响。

## 2. 比了哪些配置

| 系统 | 配置 | 为什么要比 |
| --- | --- | --- |
| `open-webui` | 默认：`all-MiniLM-L6-v2`，取 3 段，向量检索 | 装好就用的样子 |
| `open-webui-zh` | 换成 `paraphrase-multilingual-MiniLM-L12-v2` | 有中文材料的人首先会改这个 |
| `open-webui-zh-hybrid` | 同上，再开混合检索 | 最接近 Episteme 的关键词检索 |
| `open-webui-zh-k6` | 多语言模型，取 6 段 | Episteme 最多给模型 6 段，消除这个差异 |

选这几个配置的是写 Episteme 的同一个智能体，这不是 Open WebUI 能达到的上限。重排序、其他嵌入模型、改提示词都没有试。

## 3. 问答结果

单元格是“次数/总数”。“引用到位”沿用之前的规则：引用来自正确文件，且引用的文字里有答案。

| 指标 | Episteme | 贴全部材料 | OW 默认 | OW 多语言 | OW 混合 | OW 取 6 段 |
| --- | --- | --- | --- | --- | --- | --- |
| 直接题答对 | 30/30 | 30/30 | 7/30 | 25/30 | 26/30 | 27/30 |
| 第一轮同义改写题答对 | 15/18 | 18/18 | 0/18 | 15/18 | 15/18 | 15/18 |
| 新同义改写题答对 | 18/18 | 18/18 | 5/18 | 11/18 | 12/18 | 18/18 |
| 跨文档题答对 | 3/3 | 3/3 | 1/3 | 3/3 | 2/3 | 3/3 |
| **合计答对** | **66/69** | **69/69** | **13/69** | **54/69** | **55/69** | **63/69** |
| 合计答对且引用到位 | 66/69 | 69/69 | 10/69 | 52/69 | 55/69 | 63/69 |
| 无答案题拒答 | 12/12 | 12/12 | 12/12 | 12/12 | 12/12 | 12/12 |
| 无关问题，用常识答了 | 0/12 | 0/12 | 12/12 | 12/12 | 12/12 | 12/12 |
| 引用文字长度中位数（字） | 714 | 31 | 135 | 206 | 206 | 206 |
| 延迟 p50（秒） | 3.1 | 3.0 | 7.9 | 7.9 | 8.6 | 8.9 |
| 模型调用 | 84 | 93 | 186 | 186 | 186 | 186 |
| token（万） | 15.4 | 23.8 | 14.2 | 15.4 | 15.5 | 19.7 |
| 出错 | 0 | 0 | 0 | 0 | 0 | 0 |

**定位句子：** Episteme 答对且定位到答案所在句子的是 65/69，定位句中位数 31 字；贴全部材料是 69/69，靠模型自己引用。Open WebUI 通过接口返回的引用是段落，不细到句子。

**新加的判定：** 第二轮的“拒答”只看有没有“没有”“无法”这类词，“材料里没有，但法国的首都是巴黎”也算拒答。按旧规则 Open WebUI 有 10/12 到 12/12 的拒答，读原文后发现这个数字是错的，所以加了 `answeredAnyway`：回答里出现常识答案就算用常识答了。已保存的回答用 `--rescore` 重新判分，没有多花模型调用。

## 4. 能力走查

这部分在 Open WebUI 上实际发请求，每一步的返回都在 [round-3-probe.json](results/round-3-probe.json) 里。Episteme 一列来自[第二轮](round-2.md)的任务走查和测试。

| 能力 | Open WebUI 0.12.5 实测 | Episteme |
| --- | --- | --- |
| 保存一条理解 | 能，用记忆或笔记 | 能 |
| 新会话用上修正后的内容 | 能，记忆实测答出修正后的 80% | 能 |
| 修正后保留旧说法 | **经接口更新时不保留。** 记忆和笔记都是原地覆盖。笔记数据里有 `versions` 字段，但接口更新没有写入；网页端会不会写入没有测 | 保留修正历史 |
| 记忆标明依据 | 记忆只有内容、类型、路径等字段，没有来源字段 | 有来源（G3 之前的旧节点没有） |
| 只读共享 | 能，共享前另一个人 403，只读的人改也是 403 | 能 |
| 作者修正后读者看到什么 | 直接看到新内容，看不到改过什么 | 作者出新版不会改变别人已引用的内容，`tests/workbench-sharing.test.ts` 有断言 |
| 另一个人提问时引用 | 能，回答带 `[1]`，来源指向笔记，但来源信息里没有作者 | 能，跨身份引用 |
| 学习计划、速通、深学、练习 | `routers` 目录里搜不到相关接口，没有运行验证 | 有 |

这张表只说明这个版本、这些接口上观察到的结果，不等于 Open WebUI 做不到。它还有 Episteme 没有的能力，比如多种文档格式、向量和混合检索可配置、细粒度权限，这一轮都没有评估。

## 5. 问题出在哪

- **Open WebUI 答错基本是因为没检索到。** 取 6 段时，63 次答对都检索到了答案，另外 6 次没检索到。默认配置 69 次里只有 14 次检索到答案。所以差距来自检索，不是模型。
- **取几段影响很大。** 从 3 段到 6 段，新同义改写题从 11/18 升到 18/18。语料只有十来个片段，6 段已经占了不小比例，语料变大后这个效果未必还在。
- **两边的错题不同。** Episteme 错在 p1；Open WebUI 取 6 段时错在 d10 和 p2。关键词和向量的盲区确实不同，但只有这几道题，不能推出更一般的结论。
- **延迟不能直接比。** Open WebUI 每题调用模型两次，一次生成检索词，一次回答，还要在本机算嵌入。Episteme 少的调用有一部分是相关性门槛挡下的问题。
- **无关问题的差异来自提示词。** Open WebUI 的默认 `RAG_TEMPLATE` 明确要求：上下文里没有而模型知道时，说明这一点并用自身知识回答。这对通用聊天合理，对“只信材料”的学习场景不合适。这个模板可以配置，改了可能就会不同，这一轮没有试。

## 6. 维护成本

| 项目 | Episteme | Open WebUI 0.12.5 |
| --- | --- | --- |
| 安装大小 | 克隆后 276 MB | 虚拟环境 1.7 GB，245 个包 |
| 嵌入模型 | 不需要 | 默认模型下载约 930 MB，多语言模型约 4.5 GB。它会下载仓库里所有格式 |
| 首次启动 | 无下载 | 要先下载模型才响应：默认模型超过 10 分钟，多语言模型超过 40 分钟（取决于网络） |
| 再次启动 | 约 75 毫秒（不含模块加载） | 50–85 秒 |
| 许可证 | 仓库还没有 LICENSE | Open WebUI License，类 BSD，附品牌条款 |

Open WebUI 的品牌条款只在超过 50 名用户时才禁止改动品牌，这轮只是运行，不涉及。

## 7. 这轮的局限

- **作者偏差依然存在：** 题目、配置和判分都出自写 Episteme 的同一个智能体，这一轮中途就发现判分和取段数两处对比不公平，修了之后可能还有没发现的。
- **规模太小：** 四份文档、31 道题，每题 3 次不是独立样本。66 和 63 的差距不能当成结论。
- **判分粗糙：** 正则只查关键事实。例如 Open WebUI 答 p2 时列了几个相关数字并说明没有统一时长，也只算错。
- **一个模型，一种语言，一种格式：** 全是中文 Markdown，Open WebUI 在格式支持上的优势完全没有体现。
- **只走接口，没有真人：** 没有用它的网页，没有测上手难度、审阅负担和学习效果，所以**不对学习效果和易用性做任何判断**。
- **网页端可能有接口之外的行为：** 比如笔记的版本记录。
- **取 6 段那组单独跑：** 和其他几组不是同一时间。

## 8. 下一轮的决策依据

| 发现 | 决定 |
| --- | --- |
| 配好的 Open WebUI 问答接近 Episteme | 问答不是差异点，不再为追这几次答对投入 |
| 它已经能保存、共享、引用，覆盖了不少场景 | **Episteme 值得存在的理由只剩**修正历史、来源、确认流程和学习流程。这要真人使用才能验证，是目前最大的未知 |
| 只信材料、不用常识作答，是 Episteme 现在的实际差异 | 保留，但要在真人使用时确认用户是否在意 |
| Open WebUI 依赖大、品牌条款有约束 | 不把它并入 Episteme；需要时用它做对照，不复用代码 |
| 向量检索能解决部分同义改写题，但要付出下载和存储代价 | 暂不引入，等更大语料的数据 |
| 接口更新不写版本 | 如果要下结论，下一轮在网页端再测一次 |

**值得质疑的功能：** 如果真人使用后发现不在意修正历史和确认流程，那么 Episteme 的问答和共享功能就没有继续自己维护的理由，应该认真考虑改为在 Open WebUI 之类的产品上做学习流程。
